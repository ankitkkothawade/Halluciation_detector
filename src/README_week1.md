## What I could NOT run here, and why

This was built in a sandboxed environment whose network access is limited to package
registries (PyPI, npm, GitHub) — it cannot reach **huggingface.co**, **Yale's Spider
host**, or **api.groq.com**. So two things in the Week 1 plan are scaffolded but
unexecuted:

1. **Downloading Spider.** `src/generate_eval_set.py` assumes Spider's `dev.json` /
   `train_spider.json` have `db_id`, `question`, `query` keys and a matching
   `database/<db_id>/<db_id>.sqlite` file — this is my best understanding from training
   data, **not something I fetched and confirmed this session.** The script's first
   action is to print the keys of record 0 so you can sanity-check this yourself before
   trusting anything downstream.
2. **Calling Groq to generate SQL.** The client code is real and tested (see above),
   but no request was actually sent — you need your own `GROQ_API_KEY`.

## Known limitations of Layer 1 (stated up front, not discovered later)

From `schema_linking.py`'s docstring:
- Unqualified columns are checked against the union of all referenced tables' columns,
  not resolved to one specific table — can under-detect ambiguous-but-wrong unqualified
  columns.
- CTEs are not modelled as virtual tables — a query referencing a CTE alias will be
  flagged as an unknown table unless you extend `schema` to include CTE output columns.
- Execution catches runtime errors but **cannot** catch a query that runs successfully
  and returns a plausible-but-wrong result — that's exactly the gap Week 2's
  metamorphic-testing layer is meant to close.
